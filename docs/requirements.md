Ты — senior full-stack разработчик, системный архитектор и UX-дизайнер промышленного ПО.

Твоя задача — создать для меня полноценное приложение для планирования, запуска и контроля заказов в производстве металлоконструкций.

Это НЕ Excel в браузере.
Это НЕ копия 1С.
Это НЕ ERP целиком.

Мне нужна отдельная современная производственная система, которая:

* получает заказы;
* позволяет заводить их вручную или в будущем синхронизировать с 1С;
* хранит несколько позиций внутри одного заказа;
* позволяет задавать цену каждой позиции;
* позволяет держать заказ в закупке до готовности;
* позволяет заранее задать маршрут;
* дает Планеру право самостоятельно решить, когда и как запускать заказ;
* создает производственные запуски;
* распределяет задачи по участкам;
* показывает сотрудникам только их участок;
* позволяет сотрудникам менять рабочие статусы;
* считает фактическое время;
* оперативно сообщает Планеру о проблемах;
* контролирует сроки;
* показывает риск просрочки;
* хранит историю;
* собирает аналитику.

Не анализируй чертежи.

Не определяй технологию производства самостоятельно.

Не придумывай функции производственных участков.

Не придумывай производственные правила, которых я не описала.

UX-решения и техническую архитектуру предлагать можно.

# 1. ГЛАВНАЯ РОЛЬ — ПЛАНЕР

Главная роль приложения называется:

ПЛАНЕР.

Это моя роль.

Планер — главный пользователь производственной системы.

Планер должен иметь максимальные рабочие права.

Планер должен видеть ВСЁ производство и иметь возможность управлять им.

Планер может:

* создавать заказы;
* редактировать заказы;
* архивировать или удалять данные с подтверждением;
* создавать позиции заказа;
* редактировать позиции;
* изменять количество;
* задавать цену каждой позиции;
* изменять цену;
* задавать сроки;
* менять сроки;
* переводить заказ в закупку;
* менять данные закупки;
* создавать маршруты;
* редактировать маршруты;
* создавать производственные запуски;
* запускать часть заказа;
* запускать часть количества позиции;
* создавать несколько запусков одного заказа;
* менять приоритет;
* видеть все участки;
* видеть всех сотрудников;
* видеть все задачи;
* менять статусы;
* управлять очередностью;
* видеть фактическое время;
* видеть проблемы;
* получать уведомления;
* видеть аналитику;
* управлять сотрудниками;
* создавать учетные записи;
* привязывать сотрудников к участкам;
* управлять основными справочниками.

Не делай отдельного «Администратора» главной рабочей ролью.

Основная управляющая роль системы — ПЛАНЕР.

# 2. СОТРУДНИК УЧАСТКА

Вторая основная роль:

СОТРУДНИК УЧАСТКА.

У каждого сотрудника должна быть своя учетная запись.

Учетная запись содержит как минимум:

* логин;
* безопасно сохраненный пароль;
* имя;
* фамилию;
* роль;
* участок;
* активность учетной записи.

После входа сотрудник должен попадать прежде всего на свой рабочий экран.

Например:

МОЙ УЧАСТОК — ГИБКА

Он не должен видеть весь производственный интерфейс Планера.

# 3. ПРАВА СОТРУДНИКА

Сотрудник должен видеть задачи своего участка.

Он должен иметь возможность:

* открыть задачу;

* видеть позицию;
* видеть количество;
* видеть срок;
* видеть приоритет;

* видеть текущий статус;
* начать работу;
* остановить работу;
* указать причину остановки;
* возобновить работу;
* завершить работу;
* оставить комментарий;
* видеть фактически затраченное время.

Сотрудник НЕ должен без дополнительных прав:

* менять цену;

* видеть общую финансовую аналитику;
* управлять пользователями.

# 4. ДОСТУП ПО УЧАСТКАМ

Сотрудник должен получать данные только своего участка.

Ограничение должно работать не только во frontend.

Backend тоже должен проверять права.

Нельзя сделать так, чтобы сотрудник участка «Гибка» просто вызвал API участка «Сварка» и получил данные.

Используй нормальный RBAC.

# 6. ЗАКАЗЫ

Заказ может:

* создаваться вручную;
* импортироваться;
* в будущем синхронизироваться с 1С.

Не привязывай ядро приложения жестко к 1С.

Пример:

Integration Layer

Mapping

Внутренняя модель приложения.

Поля синхронизации должны быть настраиваемыми.

# 7. ПОЗИЦИИ ЗАКАЗА

Один заказ может содержать несколько позиций.

Каждая позиция должна быть отдельной сущностью.

Для позиции предусмотреть:

* ID;
* заказ;
* наименование;
* артикул / обозначение;
* количество;
* цену за единицу;
* общую стоимость;
* статус;
* комментарий.

Цена задается на каждую позицию отдельно.

Стоимость позиции:

количество × цена за единицу.

Стоимость всего заказа:

сумма стоимости всех позиций.

Пример:

Заказ №1000

Позиция 1
10 шт.
15 000 ₽/шт.
150 000 ₽

Позиция 2
3 шт.
40 000 ₽/шт.
120 000 ₽

Итого:
270 000 ₽.

# 8. ЧАСТИЧНАЯ ГОТОВНОСТЬ И ДЕНЬГИ

Приложение должно корректно работать, если готова только часть заказа.

Например:

Общая стоимость:
1 000 000 ₽.

Готовые позиции:
700 000 ₽.

В производстве:
300 000 ₽.

Не считать весь заказ готовым, если готова только часть.

Финансовая аналитика должна иметь возможность работать на уровне позиций.

# 9. ЗАКУПКА

Заказ может существовать в системе, но еще не быть готовым к запуску.

Для этого существует отдельный процесс:

ЗАКУПКА.

Закупка НЕ является производственным участком.

Заказ в закупке может уже иметь:

* позиции;
* цены;
* конечный срок;
* заранее сформированный маршрут.

Но производственного запуска еще нет.

* фактическая дата готовности;
* конечный срок заказа;
* ответственный;
* статус;
* комментарий.

* что находится в закупке;

Использовать современное рабочее представление:

* статусные индикаторы;
* сортировку;
* фильтры;

Слева:

ДОСТУПНЫЕ УЧАСТКИ.

Справа:

МАРШРУТ.

Например:

1. Лазер
2. Гибка
3. Сварка
4. ОТК.

* добавление;
* изменение порядка;
* разные маршруты для разных позиций;
* параллельные ветки.

Не накладывай технологические ограничения без моего требования.

# 19. ЗАДАЧА УЧАСТКА

После производственного запуска создаются рабочие задачи.

# 21. СТАТУСЫ

Как базовые рабочие состояния предусмотреть:

* К запуску
* Запущено в производство
* В работе
* Остановлено

Но архитектура не должна зависеть от жестко прошитого списка.

Если сотрудник останавливает задачу:

он ОБЯЗАН указать причину.

Причина остановки

Комментарий

Подтвердить.

Причины могут храниться в справочнике.

Не придумывай окончательный список причин без моего указания.

# 23. УВЕДОМЛЕНИЕ ПЛАНЕРУ О ПРОБЛЕМЕ

Если сотрудник остановил работу или сообщил о проблеме, Планер должен получить уведомление оперативно.

Пример:

ПРОБЛЕМА

# 24. ЦЕНТР УВЕДОМЛЕНИЙ

Например:

🔔 4

* просрочка;

Обычные события должны храниться в истории, а уведомления — использоваться для того, что требует внимания.

# 31. АНАЛИТИКА ПРОБЛЕМ

Позже я хочу видеть:

* сколько было остановок;
* на каком участке;
* по какой причине;
* сколько длился простой;
* среднее время устранения проблемы;
* какие участки чаще всего останавливаются;
